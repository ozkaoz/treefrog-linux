## Diagnóstico

1. zhijack no ejecutó NI SU PRIMER PASO (rotación de log.txt → .prev es lo primero que
   hace tras el lock). El userland nunca llegó a la fase hijack.
2. Apareció un archivo con nombre de bytes corruptos (`%░Ç`) en cubegm/skin/ — creado
   durante la prueba #2 (no existía en el backup de 21:39). Nombre basura = escritura
   FAT corrupta.
3. Hipótesis principal: **corrupción FAT en la zona donde el deploy #2 escribió el
   vmlinux.uImage** (o clusters dañados reutilizados). hcboot lee el kernel con su
   propio driver FAT → payload corrupto → kernel muere temprano → logo eterno.
4. El kernel #1 (boot #1) demostró que NUESTRO formato/uImage arranca el sistema
   completo — el problema del boot #2 es más probable del medio (FAT) que del kernel
   (única delta de config: CONFIG_INPUT_JOYDEV=y, verificado inofensivo en strings).
